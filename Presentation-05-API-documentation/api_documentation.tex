\section{API Scope and Architecture Overview}
% -------------------------------------------------------------

This chapter documents the REST API for the Pathao Parcel Delivery Management
System. The API supports complete parcel operations from account creation,
order placement, rider dispatch, live tracking, payment handling, and delivery
verification to platform-level analytics. The documentation is based on an
OpenAPI 3.0.3 specification and follows a consistent response envelope and
JWT-based authorization model.

\subsection{Design Principles}

The API design follows the principles below:
\begin{itemize}
		\item \textbf{Role-aware access control:} every endpoint serves a specific actor,
					and server-side role checks enforce authorization boundaries.
		\item \textbf{Predictable request/response shape:} all responses follow one
					envelope, reducing frontend integration complexity.
		\item \textbf{Operational safety:} idempotency headers, explicit status machines,
					and webhook acknowledgments reduce duplicate writes and race conditions.
		\item \textbf{Traceability:} timeline events, GPS history, OTP/proof records,
					and analytics endpoints support audit and monitoring requirements.
\end{itemize}

\section{Global API Conventions}
% -------------------------------------------------------------

\subsection{Standard Response Envelope}

All endpoints return a unified payload with four top-level fields:
\texttt{success}, \texttt{data}, \texttt{error}, and \texttt{meta}. This
uniform structure helps frontend pages handle success, validation errors,
pagination, and operational metadata with one reusable parser.

\begin{lstlisting}[caption={Unified success response format}]
{
	"success": true,
	"data": { "id": "ord_01HY..." },
	"error": null,
	"meta": {
		"requestId": "req_12abc",
		"page": 1,
		"limit": 20,
		"total": 145,
		"hasNext": true
	}
}
\end{lstlisting}

\begin{lstlisting}[caption={Unified error response format}]
{
	"success": false,
	"data": null,
	"error": {
		"code": "VALIDATION_ERROR",
		"message": "Invalid payload",
		"details": [
			{ "field": "pickup.location.lat", "issue": "Must be between -90 and 90" }
		]
	},
	"meta": null
}
\end{lstlisting}

\subsection{Cross-cutting Request Conventions}

\begin{itemize}
		\item \textbf{Pagination:} \texttt{page} and \texttt{limit} are used for list endpoints.
		\item \textbf{Sorting:} many lists support \texttt{sort} with format
					\texttt{field:direction} (example: \texttt{createdAt:desc}).
		\item \textbf{Idempotency:} write endpoints that may be retried accept
					\texttt{Idempotency-Key} to prevent duplicate operations.
		\item \textbf{HTTP semantics:}
					\texttt{GET} for read, \texttt{POST} for create/action,
					\texttt{PATCH} for partial update, \texttt{DELETE} for cancellation/removal.
\end{itemize}

\section{Authentication and Authorization (Detailed)}
% -------------------------------------------------------------

Authentication is handled using JWT access and refresh tokens.
Authorization is role-based and enforced in each protected route.

\subsection{Authentication Endpoints}

\begin{tabularx}{\textwidth}{@{}p{2.5cm}p{4.4cm}X@{}}
\toprule
\textbf{Method} & \textbf{Endpoint} & \textbf{Purpose} \\
\midrule
POST & \texttt{/auth/register} & Create a new account (self-registration only for \texttt{CUSTOMER} or \texttt{RIDER}). \\
POST & \texttt{/auth/login} & Authenticate using phone/email and password; returns user and JWT tokens. \\
POST & \texttt{/auth/refresh} & Issue new access token using a valid refresh token. \\
POST & \texttt{/auth/logout} & Invalidate refresh token and end user session. \\
POST & \texttt{/auth/forgot-password} & Request reset OTP via SMS. \\
POST & \texttt{/auth/reset-password} & Reset password using OTP and new password. \\
POST & \texttt{/auth/change-password} & Change current password for authenticated user. \\
\bottomrule
\end{tabularx}

\subsection{Token Lifecycle}

\begin{enumerate}
		\item User submits credentials at \texttt{/auth/login}.
		\item Server validates credentials and returns \texttt{accessToken} and
					\texttt{refreshToken}.
		\item Client sends \texttt{Authorization: Bearer <accessToken>} in protected API calls.
		\item When access token expires, client calls \texttt{/auth/refresh}.
		\item Server returns new token pair (or denies if refresh token is invalid).
		\item Logout revokes refresh token to prevent silent re-authentication.
\end{enumerate}

\section{Critical Module Documentation (Detailed)}
% -------------------------------------------------------------

This section focuses on the most operationally important modules.

\subsection{Orders Module}

The Orders module is the central business workflow. It governs quote generation,
order creation, updates, cancellation, status transitions, and downstream
dependencies (dispatch, tracking, payment, notifications).

\subsubsection{Primary Endpoints}

\begin{tabularx}{\textwidth}{@{}p{2.2cm}p{4.4cm}X@{}}
\toprule
\textbf{Method} & \textbf{Endpoint} & \textbf{Business Function} \\
\midrule
POST & \texttt{/orders/quote} & Pre-compute distance, ETA, and price using route and pricing rules. \\
POST & \texttt{/orders} & Create order with pickup/dropoff/parcel/payment details. \\
GET & \texttt{/orders} & List orders by role with filtering, search, and date window. \\
GET & \texttt{/orders/\{orderId\}} & Retrieve complete order detail including payment and verification fields. \\
PATCH & \texttt{/orders/\{orderId\}} & Edit mutable fields before assignment stage. \\
DELETE & \texttt{/orders/\{orderId\}} & Cancel order based on role and stage permissions. \\
POST & \texttt{/orders/\{orderId\}/status} & Rider-driven operational status update with controlled transitions. \\
\bottomrule
\end{tabularx}

\subsubsection{State Transition Logic}

\begin{tcolorbox}[
		enhanced,
		colback=SuccessGreen!7,
		colframe=SuccessGreen,
		arc=4pt,
		boxrule=0.8pt,
		left=10pt, right=10pt, top=7pt, bottom=7pt,
		title={\bfseries Rider State Machine (Operational Flow)},
		fonttitle=\bfseries\color{white},
		colbacktitle=SuccessGreen
]
\texttt{ASSIGNED -> RIDER\_EN\_ROUTE\_TO\_PICKUP -> ARRIVED\_AT\_PICKUP -> PICKED\_UP}\newline
\texttt{-> IN\_TRANSIT -> ARRIVED\_AT\_DROPOFF -> DELIVERED | DELIVERY\_FAILED}
\end{tcolorbox}

\subsubsection{Important Validation Rules}

\begin{itemize}
		\item \textbf{Quote lock:} if \texttt{quoteId} is valid at order creation,
					pricing is locked.
		\item \textbf{COD enforcement:} COD orders require \texttt{codAmount}.
		\item \textbf{Edit window:} pickup/dropoff/parcel edits are allowed only in
					early statuses (before active handoff progression).
		\item \textbf{Cancellation policy:} customer cancellation is restricted after pickup,
					while admin retains broader override ability.
\end{itemize}

\subsection{Dispatch and Offer Management}

Dispatch determines how quickly a newly created order is converted into
an assigned delivery job. It supports both automated geo-search and
manual dispatcher override.

\subsubsection{Primary Endpoints}

\begin{tabularx}{\textwidth}{@{}p{2.2cm}p{4.8cm}X@{}}
\toprule
\textbf{Method} & \textbf{Endpoint} & \textbf{Operational Role} \\
\midrule
POST & \texttt{/dispatch/search} & Run automated rider search by radius and filters. \\
POST & \texttt{/dispatch/assign} & Manual rider assignment when intervention is needed. \\
POST & \texttt{/dispatch/unassign} & Remove current rider and re-queue search. \\
GET & \texttt{/offers} & List offers (rider-scoped or admin global view). \\
POST & \texttt{/offers/\{offerId\}/accept} & Rider accepts offer; competing offers are canceled. \\
POST & \texttt{/offers/\{offerId\}/decline} & Rider declines with optional reason. \\
\bottomrule
\end{tabularx}

\subsubsection{Dispatch Pipeline Notes}

\begin{enumerate}
		\item Identify online riders near pickup using geospatial index.
		\item Apply filters (vehicle, rating, exclusion list).
		\item Sort by proximity.
		\item Issue offers with TTL window.
		\item On first valid accept, assign rider and cancel others.
\end{enumerate}

This flow minimizes assignment delay while preserving dispatcher control in
exception scenarios.

\subsubsection{Tracking Security Correction}

The rider location endpoints no longer accept \texttt{riderId} from clients.
Identity is now resolved from the authenticated JWT. This prevents one rider
from spoofing location updates for another rider by sending a forged ID.

Payments are implemented for both prepaid gateway transactions and cash-on-delivery.

\subsubsection{Primary Endpoints}

\toprule

\subsubsection{COD Reconciliation Rule}

\begin{itemize}
		\item collected == expected \Rightarrow \texttt{COD\_COLLECTED}
		\item collected  < expected \Rightarrow \texttt{COD\_UNDERPAID}
		\item collected  > expected \Rightarrow \texttt{COD\_OVERPAID}
\end{itemize}

This explicit state mapping makes cash discrepancy detection and downstream
finance reconciliation straightforward.

\section{Operational and Security Considerations}
% -------------------------------------------------------------

\subsection{Idempotency and Retry Safety}

Endpoints that can be retried by clients or gateways should accept
\texttt{Idempotency-Key} and store request fingerprints. This avoids duplicate
orders, duplicate payment sessions, and duplicate COD entries during network
instability.

\subsection{Webhook Hardening}

For prepaid and SMS webhooks:
\begin{itemize}
		\item validate provider HMAC signatures,
		\item whitelist provider IP ranges when possible,
		\item persist raw payload for forensic audit,
		\item always return deterministic acknowledgment payload.
\end{itemize}

\subsection{Location and PII Protection}

\begin{itemize}
		\item Public tracking endpoints return sanitized fields only.
		\item Phone and sensitive contact data should remain masked in public responses.
		\item Access to full location history is restricted to admin/dispatcher.
\end{itemize}

\subsection{Consistency and Observability}

Operational recommendation:
include a unique \texttt{requestId} in \texttt{meta} and correlate it across
gateway logs, database events, and SMS/webhook traces.

\subsection{High-value Regression Cases}

\begin{enumerate}
		\item Registration rejects \texttt{ADMIN}/\texttt{DISPATCHER} role values.
		\item Rider status endpoint rejects invalid state jumps.
		\item Rider location endpoint ignores forged identity fields.
		\item Offer acceptance cancels competing offers atomically.
		\item COD payment state updates correctly for under/over collection.
		\item Public tracking response never leaks direct phone numbers.
\end{enumerate}

\section{Conclusion}
% -------------------------------------------------------------

The API design provides strong coverage of parcel delivery operations with
clear separation of concerns, role-aware access control, and a consistent
response model. The most business-critical modules (Orders, Dispatch, Rider,
Tracking, Payments, Verification) are sufficiently expressive for real-world
delivery workflows, while secondary modules (Me, Users, Geo, SMS, Admin)
support usability, governance, and analytics.

The specification-level corrections applied in this revision improve security
and logic consistency without changing the overall architecture:
registration role hardening, rider status transition constraints, and secure
identity handling for rider location ingestion.
